## 관점 A 리뷰 보고서: 묶음 사이 맞물림(교차 상호작용)

### 요약
- 판정기·GUI·서브 작업·인터락 명령·음성 상태 파일·집계를 시연 흐름에 따라 겹쳐 봤습니다. 대부분의 조합은 같은 상태를 가리킵니다. 규칙 변경 D3·D4·D5의 교차, 모든 상태에서 들어오는 EMO, 차단 배너가 인터락 연결을 따라가는 것, 경고 중 서브 일시정지 뒤 EMO와 초기화가 모두 맞았습니다.
- Critical은 없습니다. Important는 1건입니다. 작업 초기화 확인창이 떠 있는 동안 물리 EMO가 들어오면 「예」 한 번으로 EMO를 누른 채 인터락이 풀립니다. 이번 네 묶음 이전(5b60a90)부터 있던 경로이고, 묶음이 만든 회귀는 아닙니다.
- Minor는 8건입니다. 주로 두 가지입니다.
  - 한 묶음의 결정이 다른 묶음의 가정을 조용히 무효로 만드는 곳: R5가 「방금 완료 버튼」 예외를 유지한다고 했지만 R2 때문에 실제로는 지워집니다. G4의 `was_running`은 작업 초기화 뒤에도 켜져 있습니다. G11 중복 방지는 D5 재시도에서 풀립니다.
  - 같은 사실을 화면·음성·결과창이 다르게 말하는 곳: 대기 중 EMO를 음성은 「진행 중」이라 합니다. 「화면에서만 차단」인데 제목·첫 줄·결과창·음성은 「인터락 작동·전기 끊김」이라 합니다.
- 확인은 코드 추적 후 격리 사본에서 했습니다. `/tmp/claude-1000/review-A`에 가짜 검출기를 넣고 손·공구·GPIO·인터락을 끈 채, 상태 파일 경로를 사본 안으로 돌려 오프스크린 콘솔로 재현했습니다. 사본은 지웠습니다. Hailo·시리얼·ESP32는 건드리지 않았고, 두 저장소의 git 상태도 깨끗합니다. 하위 에이전트 없이 여러 차례 나눠 읽었습니다.

### 발견

#### Critical
없음.

#### Important

**I-1. 작업 초기화 확인창이 떠 있는 동안 EMO가 들어오면 EMO를 누른 채 인터락이 풀리고 작업을 시작할 수 있다**
- 위치: `safety_console.py:1338`(EMO 검사) → `:1346`(`QMessageBox.question` = 모달, 중첩 이벤트 루프) → `:1359`(`_reset_work()` 다시 검사 없음) → `fsm.py:283-298`(`reset()` → `_goto(IDLE)` → `on_interlock(False)` + 피드백 NONE → RUN)
- 무엇이 겹치나: 초기화 경로의 「EMO 미복귀 거부」는 확인창을 띄우기 **전에만** 봅니다. 확인창의 중첩 루프는 GPIO 스레드에서 오는 대기열 신호(`gpio_button_signal`)를 그대로 처리합니다. 그래서 창이 떠 있는 동안 EMO가 들어오면 EMO 차단이 됩니다. 이어서 「예」를 누르면 그 차단을 검사 없이 IDLE로 풀고 릴레이에 RUN을 보냅니다. D4(EMO 해제 → IDLE)와 초기화가 같은 끝 상태로 가지만, 거부 검사는 초기화 쪽에서 새고 있습니다.
- 작업자가 겪는 것: EMO가 눌린 채 램프가 녹색이 되고 「작업 시작」 버튼이 뜹니다. 누르면 PROCESS_RUN이 됩니다. EMO는 계속 눌려 있어 새 엣지가 없으므로, 판정기는 EMO를 다시 떼었다 누를 때까지 차단하지 않습니다. `_release_block` 주석이 막으려던 「무방비 RUN」 그대로입니다.
- 고치는 방향: 확인창이 돌아온 뒤 `gpio_input.emo_active()`를 다시 봅니다. 또는 검사를 `_reset_work()` 안으로 옮깁니다. 확인창 동안 EMO 차단이 새로 생겼으면(`fsm.emo_active`) 거부하는 것도 방법입니다.
- 확인 수준: **재현함**. 확인창을 가짜로 바꾸고, 창 안에서 EMO 신호가 전달되는 것을 흉내 냈습니다. 결과: 인터락 호출 `il True → fb BLOCK → il False → fb NONE`, `emo_active()`=True 인 채 IDLE, 「작업 시작」 → PROCESS RUN. 중첩 루프가 대기열 신호를 전달한다는 것은 Qt 규칙에 따른 판단이고, 실제 GPIO로는 하지 않았습니다.
- 알려진 항목과 겹치지 않음. 이번 묶음 이전부터 있던 코드입니다.

#### Minor

**M-1. R5의 「방금 완료 버튼 예외는 유지」가 R2 때문에 실제 카메라 경로에서는 늘 지워진다**
- 위치: `fsm.py:300-308`(`forget_observation`은 `_just_done` 유지), `fsm.py:197-198`(roi None이면 `_just_done` 지움), `camera_thread.py:264-273`(재연결 시 트랙 비움), `camera_thread.py:108-126,171-172`(새 트랙은 2프레임 뒤 확정, 확정 트랙만 판정)
- 무엇이 겹치나: ① P2 + ③ R5 + ③ R2. 재연결 뒤 첫 프레임에는 확정 트랙이 없어(R2) 판정기가 roi None을 받습니다. `_last_roi`도 지워져(R5) 갭메우기가 붙들지 않으므로 `_just_done`이 지워집니다. 자가 테스트 `selftest/test_fsm.py:551-559`는 첫 None 프레임을 건너뛰고 곧바로 "B1"을 먹여서 통과합니다.
- 작업자가 겪는 것: 방금 누른 버튼 위에 손가락을 둔 채 카메라가 재연결되면, 둘째 프레임에 그 버튼이 오답 체류가 되어 약 0.3초 뒤 헛경고가 나고 서브가 일시정지됩니다. 재연결과 손가락 위치가 겹쳐야 하므로 드뭅니다.
- 고치는 방향: 둘 중 하나를 정합니다. ① 「유지」 약속을 접고 설계·주석·시험을 맞춥니다(P2의 「갭메우기 만료 = 떠남」과 같게). ② 재연결 뒤 첫 실관측 전의 None은 「떠남」으로 세지 않습니다. 시험에 R2의 None 프레임을 넣습니다.
- 확인 수준: **재현함**(순수 판정기: 망각 → None → B1×10 → WARNING). D9·P1과 인접하지만 알려진 항목은 아닙니다.

**M-2. 작업 초기화 뒤 EMO를 풀면 「비상정지로 작업 중단」 알림이 거짓으로 뜬다**
- 위치: `safety_console.py:1316-1325`(`was_running = self._stats.running`), `:1361-1381`(`_reset_work`는 집계를 비우지 않음. `:1108-1111` 주석도 이 사실을 인정)
- 무엇이 겹치나: ② G4의 판단 근거가 집계의 `running`인데, 초기화는 판정기만 되돌립니다.
- 작업자가 겪는 것: 초기화한 뒤 EMO 시험 → 해제를 하면 「비상정지로 작업 중단 — 「작업 시작」을 눌러 1단계부터 다시 합니다」가 쌓입니다. 진행 중인 작업이 없는데도 그렇습니다.
- 고치는 방향: `_reset_work`에서 `_stats.reset()`을 부릅니다. 또는 G4 판단을 `release_block()` 전 판정기 상태(IDLE 여부)로 합니다.
- 확인 수준: **재현함**(오프스크린 콘솔).

**M-3. 대기(IDLE)·완료 뒤 EMO에 음성 상태 파일이 「진행 중 · 1단계」라 하고, 완료 결과가 사라진다**
- 위치: `safety_console.py:1112-1114`(IDLE일 때만 지움), `:1426-1429`, `voice_card.py:108-124`
- 무엇이 겹치나: ③ V2(비상정지 필드)와 ① D4(EMO는 언제든 → 해제 시 IDLE). 작업 전 EMO가 `상태=BLOCK`, `세션=True`로 공개되어 카드가 「작업: … 진행 중 · 현재 진행 중인 단계: 1단계 … 비상정지」가 됩니다. 완료 뒤 결과창이 떠 있을 때 EMO를 누르면 `결과`가 빠진 상태로 덮이고, 해제하면 파일이 지워집니다.
- 작업자가 겪는 것:
  - 작업 시작 전 EMO 시연 중 「지금 몇 단계야?」 → 「1단계 진행 중, 비상정지」.
  - 완료 뒤 EMO → 「작업 결과 어때?」에 결과 대신 「1단계 진행 중」, 해제 뒤에는 「작업 시작 전」.
  - 이때 화면의 결과창은 그대로 떠 있습니다. 공정 단계 패널도 1단계를 ⛔로 칠해, 화면과 음성은 서로 맞지만 D4 뜻과는 어긋납니다.
- 고치는 방향: BLOCK이 IDLE에서 왔으면 「작업 전 · 비상정지」로 공개합니다(`세션=False` 또는 별도 필드). 완료 결과는 다음 「작업 시작」까지 유지합니다.
- 확인 수준: **재현함**(카드 원문 출력).

**M-4. 「화면에서만 차단」인데 제목·첫 줄·알림·결과창·음성은 「인터락 작동/전기 끊김」이라 말한다**
- 위치: `overlay.py:582-588`(기본 문구 「순서 위반이 계속되어 인터락이 작동했습니다」, 제목 「전기 입력 차단됨」), `safety_console.py:1199-1210,1459,1465`(알림 「전기 입력 차단됨」), `overlay_result.py:99-102`(「인터락 작동 N건」, 연결 여부 무관), `voice_card.py:125-126`(「순서를 어겨 전기 입력이 끊겼다」). 상태 파일에는 인터락 연결 필드가 없습니다.
- 무엇이 겹치나: ③ I1은 배너 둘째 줄만 바꿨습니다. ② G5는 EMO 문구만 갈랐고, 위반 문구·알림·집계·음성 카드는 연결 여부를 모릅니다.
- 작업자가 겪는 것: 인터락 미연결 차단 때 한 배너 안에 「인터락이 작동했습니다」와 「⚠ 인터락 미연결 — 화면에서만 차단 중」이 함께 뜹니다. 결과창은 「인터락 작동 1건」, 음성은 「전기 입력이 끊겼다」입니다. 발표자가 잘못 설명할 수 있습니다.
- 고치는 방향: 연결 여부를 한 곳(`interlock.connected`)에서 받아 첫 줄·알림·결과 기록·상태 파일이 같은 말을 하게 합니다.
- 확인 수준: 배너는 **재현함**(가짜 인터락으로 연결 → 끊김 전환), 결과창·음성은 코드로 확인. C18 메모(지금 실물은 CH5 우회라 연결돼도 GND가 끊기지 않음)와 인접합니다.

**M-5. 오답 공구를 계속 쥔 채 차단 → 재시도하면 「다른 공구」가 두 번 세어진다**

**M-6. U17 레시피 검사가 서브 사양의 런타임 가정을 다 덮지 않는다**
