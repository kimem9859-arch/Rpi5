## 다르다 = 2단계 최종 변환 전 위험 목록

중요한 순서다. 무엇을 고를지는 적지 않았다.

1. **최적화 수준 (C2·C4)**
   - **사실**: v1 은 수준을 적지 않아 CPU 에서 **0으로 떨어졌다**(D4:20). v2 는 **1을 명시**해 bias correction 을 얻었다(D1:9, D5:36-40). 지금 파이의 `console_v2.hef` 는 수준 1 이다. Model Zoo 원본 `yolov8n.alls` 에는 flavor 줄이 없다(D2). 새 초안은 2(finetune)다.
   - **왜 중요한가**:
     - ① 새 스크립트가 수준 줄을 빠뜨리면 v1 처럼 조용히 0이 된다. 로그에 *"Reducing optimization level to 0"* 가 없는지 확인해야 한다.
     - ② 이전 이유 「level 2 는 GPU 필요」(P2:145, P1:257)와 새 조사 「CPU 에서 막는 코드 없음」(보고서 §2.2)이 **서로 어긋난다.** 이전 근거는 「경사학습 코드가 없다」는 grep 이었고, 새 근거는 수준 결정 코드를 읽은 것이다. CPU 에서 수준 2 가 실제로 끝나는지와 걸리는 시간은 둘 다 확인하지 않았다. 참고로 v2 의 수준 1 bias correction 만으로도 652장에 29분 21초가 걸렸다(D6:86-89).
     - ③ 수준이 1 → 2 로 바뀌면 v2 HEF 와 새 HEF 의 차이에 「모델 차이」와 「양자화 수준 차이」가 섞인다. 설계 §4 의 한 단계 한 갈래 원칙과 부딪칠 수 있다.
     - ④ probe HEF(10-03)는 수준 0·보정 64장(v1 의 휴대폰 사진)이다. 정확도 판단에 쓰면 안 된다(`probe.py:5`).
2. **보정 원천 프레임 (E3·E5)**
   - **사실**: v2 보정 652장은 **VGA 가로 프레임을 Roboflow 가 세로로 1.33배 늘린 JPG** 다. 지금 런타임은 **XGA 세로 768×1024 를 `cv2.resize` 로 가로로 1.33배 늘린다**(`detector.py:110`).
   - **왜 중요한가**: 이전 이유(「파이 추론 입력과 정확히 같은 형식」, P2:151)는 회전·XGA 전환 뒤로 맞지 않는다. 보정 그림의 물체 모양·크기 분포가 런타임과 달라 활성값 범위가 어긋날 수 있다 **(추론)**. 새 초안은 원본 PNG 에 런타임 함수를 적용해 이 문제를 없앤다. 다만 기존 `늘리기640` PNG 를 쓰려면 바이트 대조가 필요하다(json `preprocess`). Roboflow 산출물을 다시 쓰면 보간 미상·JPG 재압축 문제도 돌아온다.
3. **보정 분할 (E2)**
   - **사실**: v2 는 valid 130장을 보정에 넣었다. 새 초안은 train 만 쓴다.
   - **왜 중요한가**: 새 검증관문 ②는 val 에서 int8 손실을 잰다. 탐색 목표값도 검증 몫이다. val 로 보정하면 그 비교가 낙관적으로 나올 수 있다 **(추론)**. 이전 문서에는 valid 를 넣은 이유가 없다.
4. **보정 순서·장수 (E1·E7)**
   - **사실**: Model Zoo 로더는 이름순으로 정렬하고 DFC 는 앞에서 N장을 쓴다. v1 은 실제로 **앞 64장이 영상1 50장 + 영상2 14장**으로 쏠렸다(D9).
   - **왜 중요한가**: 새 데이터도 이름이 세션순이고, 버튼 train 1213장 가운데 738장이 한 세션이다(보고서 §4). 장수를 전체보다 적게 쓰면 섞지 않을 때 같은 쏠림이 다시 생긴다. 공구는 634장뿐이다. finetune `dataset_size` 를 데이터보다 크게 적으면 `ValueError` 가 난다(보고서 §2.2).
5. **NMS 점수 문턱·json 처리 (D2·C7·D1b)**
   - **사실**: v2 HEF 의 0.2 는 Model Zoo 기본값이 그대로 들어간 것이다. 일부러 고른 값이 아니다(P3:421). 새 초안은 0.25 다. classes 는 이전에 `hailomz --classes` 가 Model Zoo 폴더 안에서 `_tmp.json` 을 만들어 넣었다(D3).
   - **왜 중요한가**:
     - ① 런타임은 0.50(`config.py:130`)·0.65(`config.py:432`)에서 거르므로, 0.2→0.25 가 운용에 주는 영향은 없을 것이다 **(추론)**. 대신 HEF 로 잴 수 있는 점수의 하한이 올라간다.
     - ② 우리 json 을 쓰면 `_tmp.json` 재사용·덮어쓰기 문제는 없어진다. 하지만 공구(3클래스)는 처음이다. DFC 는 분류층을 「출력 채널 == classes」로 찾으므로 classes 를 잘못 적으면 실패하거나 엉뚱한 층을 잡는다(보고서 §2).
6. **도구 전환: hailomz → DFC API (B1·G2)**
   - **사실**: hailomz 는 RGB 디코드(`decode_jpeg`), 이름순 로더, `--classes` 처리, 기본 alls 줄을 알아서 해 줬다.
   - **왜 중요한가**: 새 스크립트는 이것을 모두 직접 해야 한다. 빠뜨리면 조용히 틀린다. 예를 들어 `cv2.imread` 의 BGR 을 그대로 넣으면 색 순서가 뒤집힌다. probe.py 는 `BGR2RGB` 를 직접 했다(`probe.py:51`). 로컬 수정(D10)은 변환 동작에 손대지 않았으므로 이전 HEF 들의 재현성에는 영향이 없다고 본다 **(추론)**.
7. **ONNX simplify·판 (A6·A1)**
   - **사실**: v2 는 simplify=False·8.4.96 이었고, 새 초안은 True·8.4.171·torch 2.12.1 이다.
   - **왜 중요한가**: 끝 노드 이름이나 파싱 뒤 HN 층 이름(conv41… 계열)이 바뀔 수 있다. v1 은 simplify=True(8.4.63)로도 같은 6개 이름으로 파싱됐다(D4:12). 이름이 유지된다는 근거가 하나 있는 셈이다. 그래도 새 판에서는 내보낸 뒤 6개 노드와 채널(64 / nc)을 확인해야 한다(json `_확인규칙`). simplify 를 껐던 이유는 기록에 없다.
8. **finetune 이 새로 들어감 (C4)**: 이전 HEF 는 모두 finetune 을 거친 적이 없다. 처음 쓰는 알고리즘 경로이므로 검증관문 ①② 없이 배포하면 원인을 가를 수 없다.
9. **onnx 패키지 (A9)**: 새 학습 venv 에는 onnx 가 없어 첫 export 때 자동 설치를 시도한다(환경 변경). 참고로 이전에 export 한 venv(`dev/ai_model/.venv`)에는 onnx 1.22.0 이 있지만 ultralytics 는 8.4.96 이다(데스크톱 dist-info).
10. **기록 (H2)**: 이전 `.alls`·`.onnx`·보정 폴더·NMS json 은 데스크톱에만 있다. 데스크톱 상태가 바뀌면 v2 HEF 를 재현하거나 대조할 수 없다. 새 기록 항목이 이 문제를 해소한다.
11. **검증 (H3)**: 이전에는 HAR 5항목과 로그 문구만 확인했고, 에뮬레이터로 int8 손실을 잰 적은 없다. 그래서 v2 대비 새 HEF 가 좋아졌는지는 새 관문 ②④에서만 답할 수 있다.
12. **수준과 압축의 관계 (C3, 같다지만 주의)**: 압축 0 은 같다. 그러나 v2 의 0 은 「수준 ≤1 이라 자동으로 0」(D5:20)이었다. 새 초안은 수준 2 이므로 0 을 **명시하지 않으면** 기본 규칙(파라미터 20M 초과 시에만 1)을 따른다. yolov8n 이면 그래도 0 이지만, 명시 줄이 빠지지 않았는지 확인한다.
13. **(참고) 옛 2026-04 경로**: `convert_to_hef.sh` 와 `.bash_history` 31-38행은 `hailo8l`, `--use-random-calib-set`(무작위 보정), alls·NMS 없음, 옛 14클래스용이다. 재사용하면 장치가 다르고 NMS 없는 HEF 가 나온다. 배포 HEF 는 없다.

## 확인 못 한 것

- **v2 ONNX 를 내보낸 장치(CPU/GPU)**: ONNX 메타 `args` 에 device 가 없다.
