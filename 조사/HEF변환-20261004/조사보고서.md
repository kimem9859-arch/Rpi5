## §1. ONNX 내보내기 (ultralytics 8.4.171)

### 기본값과 근거

| 인자 | 8.4.171 기본 | 근거(S1) | 무엇에 맞춘 값인가 |

| `quantize` | `None`(FP32) | `default.yaml:58`. `half`·`int8` 는 **폐기되고 `quantize` 로 옮겨졌다**(`cfg/__init__.py:613-622`) | FP32 그래프 |
| `device` | `None` → CPU | `exporter.py` 장치 선택 · S5 export 표 | — |
| ONNX 형식이 받는 인자 | `batch, data, dynamic, quantize, opset, simplify, nms, fraction` | `exporter.py:171` | — |

- 입력과 출력 이름은 `input_names=["images"]`(`exporter.py:1152`), 출력은 `output0` 하나(`:1109`)다.
- ⚠️ **학습 venv 에 `onnx` 가 없다**(S11: `ModuleNotFoundError: No module named 'onnx'`). `export_onnx` 는 `check_requirements(requirements)`(`exporter.py:1093`)를 부르고 `AUTOINSTALL = env_bool("YOLO_AUTOINSTALL", True)`(`utils/__init__.py:71`)이므로, **처음 내보낼 때 학습 venv 에 onnx 와 onnxslim 을 pip 로 설치하려 한다.** 환경을 바꾸는 일이므로 학습이 끝난 뒤 사용자 승인을 받고 해야 한다.

### Hailo 쪽 공식 값 (두 1차 출처가 일치한다)

- Model Zoo 재학습 안내(S3 `training/yolov8/README.rst:94`): `yolo export model=/path/to/trained/best.pt imgsz=640 format=onnx opset=11  # export at 640x640`
- ultralytics 자체 Hailo 경로(S1 `exporter.py:1718`): `self.args.opset = 11` 다음 `self.export_onnx()` 를 호출한다. simplify 는 기본값(True)을 그대로 쓰고, 끝 노드 이름은 `/model.{head_index}/cv{2,3}.{i}/…` 를 전제한다(`:1716`).
- ultralytics 문서(S5 hailo): *"Each HEF is compiled for a fixed `imgsz`"*, *"Dynamic shapes…are not supported"*.

### 우리 상황: 그대로/바꿈

| 인자 | 판정 | 값 | 이유 |
|---|---|---|---|
| `opset` | **바꿈** | 11 | 공식 두 경로가 모두 11이다. 기본 18이 DFC 3.33.1 파서에서 되는지는 확인하지 않았다(파서의 opset 상한을 찾지 못했다). |
| `imgsz` | **명시** | 640 | 런타임 `YOLO_INPUT_SIZE = 640`(S4 `config.py:137`). 기본값이 학습 imgsz 라 다른 해상도로 학습한 모델이면 조용히 그 크기로 나간다. |
| `batch` | 그대로 | 1 | — |
| `dynamic` | 그대로 | False | Hailo 는 고정 크기만 받는다(S5). |
| `simplify` | 그대로 | True | ultralytics Hailo 경로가 이 상태로 끝 노드 이름을 쓴다(`exporter.py:1716-1726`). |
| `nms` | 그대로 | None | NMS 는 HEF 의 `nms_postprocess` 가 붙인다(§2). `nms=True` 면 `NMSModel` 로 감싸 그래프 뒤에 NMS 연산이 붙고(`exporter.py:1134`), 모듈 경로가 바뀌어 끝 노드 이름이 달라질 수 있다 **(추론)**. |
| `quantize`/`half` | 그대로 | None(FP32) | int8 양자화는 DFC 가 한다. ONNX `quantize=8` 은 onnxruntime 정적 양자화를 넣는다(`exporter.py:1091`). |

### 함정
1. **imgsz 기본값이 학습값이다.** 다른 해상도로 학습한 모델에 imgsz 를 빼면 HEF 입력이 640이 아니게 되고, `detector.py:110` 의 640 리사이즈와 어긋난다.
2. **onnx 자동 설치.** 위에 적은 대로 학습 venv 가 바뀐다.
3. **nms=True·quantize=8·half 를 쓰지 않는다.** 끝 노드 앞의 그래프는 같더라도 이름과 정밀도가 바뀔 수 있다.

## §2. DFC 3단계 (parse · optimize · compile), DFC 3.33.1

### 2.1 parse (translate)

**기본값과 근거**
- API: `ClientRunner(hw_arch=…).translate_onnx_model(model, net_name, start_node_names=None, end_node_names=None, net_input_shapes=None, …)` (S2 `runner/client_runner.py:1136-1190`). docstring: *"The order of the output nodes is determined by the order of the end_node_names."*
- CLI: `hailo parser onnx … [--start-node-names …] [--end-node-names …] [--hw-arch {hailo8,hailo8r,hailo8l}] [-y]`. `-y` 설명: *"Assume "yes" as an answer to all parser recommendations"* (S2 `hailo parser onnx --help`).
- **시작 노드**: 지정하지 않으면 그래프 입력(`images`)부터 시작한다. ultralytics Hailo 경로도 끝 노드만 넘긴다(`exporter.py:1726`).
- **끝 노드(yolov8n)**: ultralytics 는 Detect 헤드의 **회귀/분류 마지막 Conv 6개**에서 자른다(`exporter.py:1714-1717`).
  ```
  /model.22/cv2.0/cv2.0.2/Conv  /model.22/cv3.0/cv3.0.2/Conv   (stride 8)
  /model.22/cv2.1/cv2.1.2/Conv  /model.22/cv3.1/cv3.1.2/Conv   (stride 16)
  /model.22/cv2.2/cv2.2.2/Conv  /model.22/cv3.2/cv3.2.2/Conv   (stride 32)
  ```
  `head_index = len(self.model.model) - 1`(`:1674`)이고, yolov8 은 Detect 가 22번 층이다(S1 `cfg/models/v8/yolov8.yaml` 마지막 줄 `[[15, 18, 21], 1, Detect, [nc]]`). cv2 = 상자 회귀(4×reg_max 16 = 64채널), cv3 = 클래스(nc 채널)다.
- Model Zoo 는 끝 노드를 적지 않고(`base/base.yaml:36-39` `nodes: [null, null]`, `yolov8n.yaml` 에도 없음) `y=True` 로 파서 추천을 받아들인다(S3 `core/main_utils.py:102,112`). DFC 파서에는 YOLO 계열 NMS 구조를 찾는 코드가 있다(S2 `onnx_translator.py:2550` 문자열 *"NMS structure of … (or equivalent architecture) was detected."*. 그 안쪽 논리는 §한계 참조).

**우리 상황**: 끝 노드 6개를 **명시**하고 순서를 (reg8, cls8, reg16, cls16, reg32, cls32)로 고정한다. 이름은 우리 ONNX 를 열어 확인해야 확정된다. `변환설정.json` 에는 예상 이름과 확인 규칙을 함께 적었다.

### 2.2 optimize (int8 양자화)

**입력 정규화를 모델 안에 넣는 방법**
- 모델 스크립트(.alls) 첫 줄 `normalization1 = normalization([0.0, 0.0, 0.0], [255.0, 255.0, 255.0])` (S3 `alls/generic/yolov8n.alls:1`, S1 `exporter.py:1728` 도 같다).
- 그 결과 보정 데이터와 런타임 입력은 **정규화하지 않은 0~255** 여야 한다. DFC 튜토리얼(S2 `DFC_2_Model_Optimization_Tutorial.ipynb` 셀 7): *"if a normalization layer has been added to the model, the calibration set should not be normalized."* · *"if normalization has been added to the model, remove the normalization code from the pre-processing code, and feed un-normalized images to the model."*
- Model Zoo 는 `normalize_in_net: true`, mean 0, std 255 일 때 전처리에서 정규화를 빼고(`core/main_utils.py:200-201`), `yolo_v5` 전처리는 float32 로 바꾸기만 한다(`core/preprocessing/detection_preprocessing.py:142-163`). ultralytics 도 `batch["img"]`(uint8)를 float32 로만 바꿔 넘긴다(`exporter.py:1780-1782`).

**보정 셋: 크기·순서·형식 (S2)**
- 통계 수집에 쓰는 장수 기본값은 **64**다. `CalibrationConfig.calibset_size: int = Field(64, …)` (`acceleras/model_optimization_config/mo_config_model.py:585`), 배치 기본 `DEFAULT_BATCH_SIZE = 8` (`acceleras/utils/acceleras_definitions.py:1078`).
- **받은 순서대로 앞에서 N장을 쓴다(섞지 않는다)**: `self._dataset = self._unbatched_dataset.take(calibset_size).batch(batch_size)` (`algorithms/stats_collection/stats_collection.py:84`).
- 권장 장수: `RECOMMENDED_DATASET_SIZE = 1024` (`acceleras_definitions.py:469`). 튜토리얼 셀 2: *"it is recommended to have at least 1024 inputs and to use a GPU."*
- 장수 검사: 기본값보다 데이터가 적으면 경고를 내고 줄인다. **명시한 값보다 적으면 `ValueError`** 다(`algorithms/optimization_algorithm.py:195-226`, *"Required {dataset_size_key} is …, but dataset contained only … images"*).
- 형식: `tf.data.Dataset` 의 `((h, w, c), image_info)`, numpy 배열, npy 디렉터리 등(`client_runner.py:2161-2205`).

**최적화 수준 (S2 `mo_config.py`)**
- docstring(`:64-67`): *"compression_level: 1 · optimization_level: 2 for GPU and 1024 images, 1 for GPU and less than 1024 images, and 0 for CPU only."*
- 수준별 내용(`:74-80`, *"might change every version"*): `0 - Equalization` · `1 - Equalization + Iterative bias correction` · `2 - Equalization + Finetune with 4 epochs & 1024 images` · `3 - … Adaround with 320 epochs & 256 images` · `4 - … Adaround … 1024 images`.
- 기본 결정 논리(`:137-170`): 데이터가 1024장보다 적으면 1, GPU 가 없으면 0. 경고 문구는 *"Reducing optimization level to … (the accuracy won't be optimized and compression won't be used)"*.
- **직접 지정한 수준은 GPU 유무와 상관없이 그대로 쓴다**(`:199-201` `if self.optimization_level is not None: optimization = self.optimization_level`). CPU 에서 수준 2 이상을 막는 코드는 찾지 못했다(`has_gpu` 는 기본 수준 결정 `tools/mo_script_parser.py:117-129` 과 다중 GPU 분산 `distributed_utils.py:51-52` 에서만 쓰인다).
- 수준 0이면 경고한다(`:232-236`): *"Running model optimization with zero level of optimization is not recommended for production use and might lead to suboptimal accuracy results"*.
- 수준 2의 finetune 은 `epochs=4, dataset_size=1024`(`:259`)다. 특정 알고리즘을 따로 설정하면 flavor 기본값을 덮어쓴다(`:61-62` *"any algorithm-specific configuration will override the flavor's default config"*).
- 알고리즘 근거 논문: Equalization(Meller2019), IBC(Finkelstein2019), QFT(Finkelstein2022) (S3 `docs/OPTIMIZATION.rst:30-31`).

**압축 수준(4비트 가중치)**
- 기본값은 수준 2 이상이면서 **파라미터가 2천만 개를 넘을 때만** 1이고, 아니면 0이다(`mo_config.py:186-188`, `MINIMUM_PARAMS_FOR_COMPRESSION = 20e6` `acceleras_definitions.py:471`). yolov8n 은 3.2M(S3 `yolov8n.yaml:19`)이라 **기본 압축은 0, 즉 4비트 없음**이다.
- 정확도를 올리는 방법으로 튜토리얼 셀 27이 드는 것: 1024장 이상과 GPU, 수준 올리기, 압축 낮추기, *"Set the output layer(s) to use 16-bit accuracy using the command quantization_param(output_layer_name, precision_mode=a16_w16). Note that the DFC will set 16-bit output automatically for small enough outputs."*

### 2.3 compile

- `runner.compile()` 은 HEF 바이트를 돌려준다(S2 `client_runner.py:899`, S1 `exporter.py` 의 `(… .hef).write_bytes(runner.compile())`).
- 컴파일러 최적화 수준의 기본은 **1**, 최대는 2다(S2 `allocator/performance_params.py:7-13` `DEFAULT_OPTIMIZATION_LEVEL = OptimizationLevel.ONE`). max 가 아니면 이런 안내가 나온다: *"To achieve optimal performance, set the compiler_optimization_level to "max" … Note that this may increase compilation time."* (`allocator/hailo_tools_runner.py:505-512`).
- Model Zoo `--performance` 는 generic alls 에만 `performance_param(compiler_optimization_level=max)` 를 덧붙인다(S3 `core/main_utils.py:610-612`).
- 할당 옵션 `allocator_param(width_splitter_defuse=disabled)` 는 Model Zoo yolov8n.alls 와 ultralytics 에 모두 있다(S3 `yolov8n.alls:7`, S1 `exporter.py:1777`).

### NMS 를 HEF 에 넣기 (optimize 단계 모델 스크립트)

- `nms_postprocess("<json>", meta_arch=yolov8, engine=cpu)` (S3 `yolov8n.alls:5`, S1 `exporter.py:1776`).
- **yolov8 NMS 는 CPU(호스트)에서만 돈다.** `NN_CORE_META_ARCHS` 에는 SSD·YOLOV5·CENTERNET·YOLOV6 만 있고, YOLOV8 은 `CPU_META_ARCHS` 에만 있다(S2 `sdk_backend/script_parser/nms_postprocess_command.py:46-60`). docstring: *"engine (str): describes whether the post-process will be run on neural core or on HRT."* 따라서 `engine=cpu` 는 **파이 CPU 위의 HailoRT** 가 NMS 를 돌린다는 뜻이다.
- json 경로는 **.alls 파일 기준 상대경로**다(`nms_postprocess_command.py:292-309`, 오류 문구 *"make sure the given path is relative to the .alls file location"*).
- 분류 출력에는 시그모이드를 붙인다: `change_output_activation(<cls conv>, sigmoid)` (S3 `yolov8n.alls:2-4`, S1 `exporter.py:1774`).
- DFC 의 yolov8 기본 json(설정 파일 없이 부를 때)은 `nms_scores_th 0.001, nms_iou_th 0.7, max_proposals_per_class 100, classes 80` (S2 `tools/core_postprocess/default_nms_config_yolov8.json:2-9`)이다. 공통 기본값은 `DEFAULT_SCORES_TH = 0.3 · DEFAULT_IOU_TH = 0.6 · DEFAULT_MAX_PROPOSALS_PER_CLASS = 10`(S2 `hailo_sdk_common/hailo_nn/nms_postprocess_defaults.py:1-3`)이고, CPU 엔진의 yolov8 IoU 는 0.7 이다(`nms_postprocess_command.py:89-93`).
- json 의 reg_layer/cls_layer 가 비어 있으면 DFC 가 자동으로 찾는다. 회귀층은 출력 채널 = `reg_len*4`(64)이면서 linear 인 것, 분류층은 **출력 채널 == json 의 `classes`** 인 것이다(`nms_postprocess_command.py:99-105, 693-718`). 못 찾으면 *"Cannot infer bbox conv layers automatically"* 로 실패한다.

### 런타임 계약 (S4) — HEF 가 지켜야 할 것

- 입력: `cv2.resize(frame, (640, 640))`(**비율을 무시하고 늘림**, 보간 기본값) → `BGR2RGB` → `uint8`, `[1,640,640,3]` (`detector.py:110-114`). 입력 vstream 형식 기본은 `FormatType.AUTO`(`pyhailort.py:3651-3675`).
- 출력: 출력 vstream 은 **첫 번째 하나만** 읽는다(`list(output.values())[0][0]`, `detector.py:117`). 그 구조는 **클래스별 배열 목록**이고 각 행은 `(ymin, xmin, ymax, xmax, score)`(0~1 정규화)다(`detector.py:118-130`). HailoRT 문서(`pyhailort.py:3046-3049`): *"hailo HAILO_NMS_BY_CLASS format is a list of numpy.array where each array represents the detections for a specific class … (y_min, x_min, y_max, x_max, score)."* `InferVStreams(tf_nms_format=False)` 가 기본값이다(`pyhailort.py:865-882`).
- 클래스 이름은 코드에 고정돼 있다: `{0: "B1", 1: "B2", 2: "B3", 3: "B4", 4: "EMO"}` (`detector.py:103`). HEF 에는 클래스 이름이 들어가지 않는다.

### 함정 (우선순위 순)

1. **보정과 런타임의 전처리가 다르다.** Model Zoo(`letterbox`, 확대 허용, 114 패딩)와 ultralytics(`LetterBox(…, scaleup=False)`, S1 `data/dataset.py:337`, 기본 패딩 114·가운데 정렬 `data/augment.py:1701-1709`)는 모두 letterbox 이고, 런타임은 늘리기다. 원본 768×1024 프레임을 letterbox 하면 480×640 이미지 양옆에 회색 띠가 80픽셀씩 생기고, 런타임은 가로를 640/768, 세로를 640/1024 로 다르게 줄인다. → **보정 이미지는 런타임과 같은 함수(`cv2.resize(frame,(640,640))` 후 `BGR2RGB`)로 640×640 을 미리 만든다.** 640×640 을 넣으면 두 letterbox 모두 비율이 1이라 아무것도 하지 않는다(Model Zoo `letterbox` 코드상 dw=dh=0, ultralytics 는 **(추론)**).
2. **정규화가 두 번 걸릴 수 있다.** alls 에 정규화를 넣었으니 보정·런타임 모두 0~255 다. 보정에 `/255`(ultralytics `_transform_fn` 은 `/255.0` 을 한다. 다른 형식용이라 hailo 경로는 쓰지 않는다)나 0~1 이미지를 넣으면 범위가 틀어진다.
3. **NMS `classes` 와 층 이름이 Model Zoo 값 그대로다.** Model Zoo json 은 `classes: 80` 이고 층 이름은 그 ONNX 의 HN 이름(`yolov8n/conv41…`)이다. 우리 HN 이름은 파싱해야 안다. `--classes` 를 쓰면 Model Zoo 폴더에 `_tmp.json` 이 생긴다(우리 체크아웃에 이미 하나 있다, 열지 않음).
4. **CPU 에서 수준을 지정하지 않으면 최적화 수준 0이다.** Model Zoo yolov8n.alls 에는 flavor 줄이 없다. 우리 데스크톱 DFC 는 GPU 를 못 잡는다(§7). 그래서 hailomz 를 그대로 돌리면 수준 0, 즉 equalization 만 하고 IBC·finetune 이 없는 HEF 가 나온다.
5. **보정 순서 편향.** DFC 는 앞 N장을 그대로 쓰고(`take`), Model Zoo 는 이름순으로 정렬하며, 우리 파일 이름은 세션순이다. 기본 64장이면 첫 세션 몇 개만 보게 된다.
6. **보정 분할.** ultralytics 기본은 val(177장, 300장 미만이라 경고 `exporter.py:1055`)이다. test 를 쓰면 평가가 순환논리가 된다.
7. **공구는 1024장이 모자라다.** finetune `dataset_size` 를 1024로 명시하면 `ValueError` 가 난다. 634 로 맞춘다.
8. **아키텍처 이름.** ultralytics 경로는 `name` 을 빼면 `hailo8l` 이다.
9. **HEF 출력이 정확히 하나(NMS)여야 한다.** `detector.py` 는 첫 출력 하나만 읽는다. alls 가 빠져 NMS 가 없으면 출력이 6개가 되고 조용히 잘못 해석한다 **(추론)**. 변환 뒤 출력 vstream 개수, 형식(`HAILO_NMS_BY_CLASS`), 클래스 수가 5/3 인지 확인한다.
10. **클래스 순서.** HEF 에는 이름이 없다. `best.pt` 의 `model.names` 순서가 `detector.py:103` 의 고정 표(B1~EMO)와 같은지 기록하고 대조한다. 공구도 마찬가지다(driver·wrench·pliers 순서는 조사 요청서 기준이며 `model.names` 로 확인해야 한다).
11. **학습·PyTorch 경로와 HEF 경로의 전처리가 다르다(변환 범위 밖).** ultralytics 의 검증·예측은 letterbox 다(`engine/predictor.py:231-237`, `data/dataset.py:337`). `PyTorchDetector` 는 그 경로를 타고(`detector.py:51-53`), `HailoDetector` 는 늘린다. 같은 프레임에서 .pt 와 .hef 결과가 다른 원인에는 양자화 말고도 이 차이가 있다. `늘리기640` 데이터셋으로 학습하면 이 차이는 없어진다 **(추론, 입력해상도 시험 문서는 열지 않았다)**.
12. **소형 물체.** 작은 버튼은 stride 8 분기에 걸린다. int8 손실이 크면 출력층 16비트(`quantization_param(…, precision_mode=a16_w16)`)나 수준 3·4(Adaround)를 후보로 시험한다. 효과는 측정하지 않았다 **(추론)**.
13. **Model Zoo 체크아웃이 로컬에서 고쳐져 있다.** hailomz 를 쓰면 원본 v2.18 이 아닌 코드로 돈다(editable 설치, `hailo_model_zoo 2.18.0 /mnt/d/Hailo_DFC/hailo_model_zoo`). 재현성을 떨어뜨린다.

## §5. 결론: 자체 변환 스크립트가 필요한가

**결론: 필요하다. 다만 얇게 만든다.** DFC Python API(`ClientRunner.translate_onnx_model` → `load_model_script` → `optimize` → `compile`)를 직접 부르는 스크립트 하나로, 단계 구성은 ultralytics 8.4.171 `export_hailo`(S1 `exporter.py:1658-1810`)를 그대로 따른다.

**공식 흐름만으로 부족한 이유**

| 경로 | 막히는 점(근거) |
|---|---|
| Model Zoo `hailomz compile --yaml --ckpt --calib-path --classes` | ① 보정이 letterbox 다(§3). 미리 늘려 두면 피할 수 있다. ② 이름순 정렬 + 앞 64장. 줄이려면 alls 로 calibset 을 지정해야 한다. ③ `--classes` 가 Model Zoo 폴더에 파일을 쓴다. ④ alls 에 flavor 가 없어 CPU 에서는 수준 0이다. ⑤ 체크아웃이 로컬에서 고쳐져 있다. ⑥ OPTIMIZATION.rst 단서: 사용자 모델은 DFC 를 직접 쓰라고 한다. ⇒ 우회 방법을 다 쓰면 결국 사용자 alls·json·보정 폴더를 우리가 만드는 셈이고, 그건 자체 스크립트와 같다. |
| ultralytics `model.export(format="hailo", name="hailo8")` | ① ultralytics·torch 와 DFC·TF 가 **한 venv** 에 있어야 한다(`exporter.py:1661-1662` 에서 `tensorflow` 와 `hailo_sdk_client` 를 import). 우리는 둘이 분리돼 있고, 고정 버전도 부딪힌다: DFC `onnxruntime==1.18.0`·`onnx==1.16.0`·`numpy==1.26.4`(S2 METADATA) vs ultralytics export-base `onnxruntime>=1.20.0`·`onnxslim>=0.1.82`(S1 METADATA). ② 보정이 `LetterBox(scaleup=False)`, 기본 val 분할이고 전처리 함수를 바꿀 인자가 없다. ③ 수준 2를 강제한다(`:1729`, CPU 에서 오래 걸림). ④ 기본 아키텍처가 hailo8l 이다. ⇒ 레시피(끝 노드, alls, NMS json 구성)는 **좋은 1차 참고**지만 그대로 쓸 수 없다. |

**스크립트가 직접 맡아야 할 것**
1. **클래스 수와 순서**: `best.pt` 의 `model.names` 에서 읽어 NMS json `classes` 에 넣고, 이름 순서를 기록하고, `detector.py` 표와 대조한다.
2. **끝 노드**: 6개를 명시하고, ONNX 에서 있는지·채널 수(64 / nc)를 확인한 뒤 넘긴다. 파싱 뒤 HN 출력층 이름을 읽어(`exporter.py:1740` 방식) sigmoid 줄과 bbox_decoders 를 채운다.
3. **전처리**: 보정 이미지를 런타임과 **같은 함수**로 만든다(BGR 원본 → `cv2.resize(…,(640,640))` → RGB → uint8). 정규화는 alls 한 줄로만 한다.
4. **보정 분할**: train 만 쓰고, 고정 시드로 섞고, N=min(1024, train 장수)로 하며, 파일 목록을 기록한다.
5. **최적화 설정**: 수준·압축·calibset·finetune 크기를 alls 에 명시해, GPU 유무에 따라 결과가 바뀌지 않게 한다.
6. **기록**: DFC·ultralytics·torch·onnx 판, `.pt`/`.onnx`/`.hef` sha256, 끝 노드와 HN 출력층 대응, alls 전문, NMS json, 보정 목록·시드, DFC 로그의 실제 적용 수준(*"Using default optimization level"* / *"Reducing…"* 문구), 컴파일 로그, HEF 출력 vstream 정보.
7. **검증 관문**(실행은 별도 태스크): ① 에뮬레이터 `SDK_NATIVE` 와 원본 ONNX 비교 → ② `SDK_QUANTIZED` 와 `SDK_FP_OPTIMIZED` 를 val 에서 비교(튜토리얼 셀 9) → ③ 파이 HailoRT 4.23 에서 HEF 로드, 출력 1개·클래스 수 확인 → ④ 같은 프레임에서 .pt(늘린 입력)와 .hef 결과 대조. 실HW 검증 전까지는 ⏸ 다.

## §7. DFC GPU 사용 (사용자 결정 항목)

**DFC 3.33.1 / 3.34 의 GPU 요구 (1차 출처)**
- Model Zoo v2.18·v2.19.1 `docs/GETTING_STARTED.rst:15-18`(같은 문구): *"Nvidia's Pascal/Turing/Ampere GPU architecture (such as Titan X Pascal, GTX 1080 Ti, RTX 2080 Ti, or RTX A4000) · GPU driver version 525 · CUDA 12.5.1 · CUDNN 9.10"*.
- README 배지: v2.18(DFC 3.33)과 v2.19.1(DFC 3.34) 모두 `Tensorflow-2.18.0`, `CUDA-12.5.1` 이다. **3.34 도 GPU 스택은 바뀌지 않았다**(배지 기준).
- DFC 3.33.1 이 고정하는 것(S2 METADATA): `tensorflow==2.18.0`, `keras==3.5.0`. 설치된 TF 빌드 정보(S11 `tf.sysconfig.get_build_info()`): `'cuda_compute_capabilities': ['sm_60', 'sm_70', 'sm_80', 'sm_89', 'compute_90'], 'cuda_version': '12.5.1', 'cudnn_version': '9'`. **sm_120 용 기계어가 없고 compute_90 PTX 만 있다.**
- 직원 답변(S9 18385, omria Staff, 2025-12-07, DFC 3.33.0 질문): *"Officially, Blackwell (SM_120) isn't supported yet. That said, it can work with the right setup"* · *"Even with everything updated, support for Blackwell GPUs isn't official yet, so errors like `CUDA_ERROR_INVALID_HANDLE` might still pop up."* · CPU 대안(`CUDA_VISIBLE_DEVICES=-1`)은 *"fully supported and stable, just slower compared to GPU execution."* 같은 답변에서 CUDA 12.5.1 에는 드라이버 555 이상이 필요하다고 했다(GETTING_STARTED 의 525 와 다르다).
- S9 19303(2026-05-25, Michael, Staff 표시는 확인하지 못함): *"The RTX 5060 Ti (Blackwell / Compute Capability 12.0) is not currently supported by the Hailo Dataflow Compiler. The documentation specifies supported GPU architectures as Pascal, Turing, Ampere, and Ada only."* · *"For time being unfortunately there is nothing specific I can share about timelines."*
- NVIDIA(S10): RTX 5060 은 compute capability 12.0 이다. *"Application binaries that include PTX version of kernels, should work as-is on the Blackwell GPUs."* · *"A cubin generated for a certain compute capability is supported to run on any GPU with the same major revision and same or higher minor revision of compute capability."* 즉 TF 2.18 은 PTX JIT 로만 돌 수 있다. Hailo 쪽 보고에서 실패 사례(`CUDA_ERROR_INVALID_HANDLE`)가 이어진다.
- **Blackwell 지원 여부**: 2026-10-04 기준으로 DFC 3.33/3.34 에 대한 공식 지원 발표는 찾지 못했다. 3.34 도 같은 TF 2.18·CUDA 12.5.1 배지다.

**우리 데스크톱의 실제 상태 (S11)**
- GPU: `NVIDIA GeForce RTX 5060, driver 591.86, compute_cap 12.0`. 조사 시점에 학습 중이라 메모리 2758/8151 MiB 를 쓰고 있었다.
- DFC 가 GPU 를 고르는 방식(S2 `hailo_model_optimization/__init__.py:18-28`, `acceleras/utils/nvidia_smi_gpu_selector.py:8-19`): `CUDA_VISIBLE_DEVICES` 가 비어 있으면 `nvidia-smi` 를 불러 **메모리 사용률 5% 이하** GPU 를 고른다. 없으면 `CUDA_VISIBLE_DEVICES="99"` 로 두고 *"No GPU chosen and no suitable GPU found, falling back to CPU."* 를 출력한다. 이번 조사 중 import 할 때도 이 문구가 나왔다.
  - WSL 에서 `nvidia-smi` 는 `/usr/lib/wsl/lib/` 에 있는데 **PATH 에 없다**(비로그인·로그인 셸 모두). 그래서 Blackwell 문제와 별개로 자동 선택부터 실패한다.
  - 학습 중에는 사용률이 5%를 넘어 자동 선택이 되지 않는다. 학습과 동시에 쓰는 것은 설계상 막혀 있다고 보는 것이 맞다 **(추론)**.
- **CUDA 런타임과 cuDNN 이 없다**: `ldconfig -p` 에는 `libcuda.so.1`(WSL 드라이버)만 있고, `libcudart`·`libcublas`·`libcudnn` 은 시스템에도 hailo-venv 에도(`nvidia-*` 휠 없음) 없다. 따라서 지금 상태로는 TF 가 GPU 를 쓸 수 없다 **(추론: TF CUDA 빌드는 이 라이브러리들을 동적으로 불러온다)**.

**GPU 가 있으면 달라지는 것**
- **기본 최적화 수준**: CPU 0 → GPU 1(1024장 미만) 또는 2(1024장 이상)(§2.2). alls 에 수준을 명시하면 이 차이는 없어진다.
- **속도**: 튜토리얼 셀 0 *"To obtain best performance run this code with a GPU machine."* finetune(수준 2)과 Adaround(수준 3·4)는 학습형 알고리즘이라 CPU 에서 오래 걸린다. 시간은 측정하지 않았다 **(추론)**.
- **허용되는 수준**: 코드상 CPU 에서도 0~4 모두 지정할 수 있다. 막는 곳을 찾지 못했다(§2.2). 다중 GPU 분산만 GPU 2개 이상이 필요하다.
- **양자화 품질**: 같은 수준·같은 데이터면 같은 알고리즘이다. GPU 자체가 품질을 바꾼다는 근거는 없다. 실제 차이는 "기본 수준이 올라간다"와 "같은 시간에 더 높은 수준을 돌릴 수 있다"에서 온다 **(추론)**.

**CPU 의 제약**: 수준 2(finetune 4 epoch × 1024장)나 3·4(Adaround 320 epoch)를 CPU 에서 돌린 시간은 미측정이다. GPU 학습과 동시에 돌리면 CPU 경합이 생긴다 **(추론)**.
