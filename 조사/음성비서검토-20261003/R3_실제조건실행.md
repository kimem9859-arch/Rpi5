## R3 「실제 조건 실행」 검토 보고서: 음성비서 `Demo/voice_assistant.py`

### 요약
1. **데운 LLM 경로는 배선대로 돈다.** LLM 답 20건 모두 검산 「일치」 → 합성 → 전송 → `[재생 완료]` 확인까지 갔다. 발화 끝 → 답 전송 8.7~16.3초, 재생 끝까지 10.9~26.7초. 고정 wav 경로는 각각 0.8초·2.3초.
2. 🔴 **모델이 내려가 있으면(콜드) LLM은 스스로 데워지지 않는다.** 15초 타임아웃으로 끊는 순간 Ollama가 적재를 취소한다(끊은 뒤 85초까지 미적재 확인). 그래서 질문마다 17.7초 기다린 뒤 「지금은 답변할 수 없습니다」가 나온다.
3. 🔴 **LLM 대기·재생 10~20초 동안 마이크 소켓을 읽지 않는다.** 파이 수신창이 3.5초 만에 약 114KB로 찬다(실측). 이후 펌웨어 흉내(ESP32 코어 소스 그대로)에서 LLM 경로 26회 중 24회 업링크가 끊겼다. 그 사이 한 말은 사라지거나, 답이 끝난 뒤 늦게 처리돼 엉뚱한 띠링이 울린다.
4. 🔴 **설계 질문 「펌프 퍼지 끝났어?」「지금 다음 순서 뭐야?」에 현재 버튼이 B2인데 「버튼 B3를 누르시면 됩니다」라고 답한다.** 5/5 같은 답(temperature 0)이고 검산도 통과한다. 비서가 순서 위반을 권하는 셈이다.
5. **재생 확인:** 저장소 `fake_glass`는 응답 줄을 보내지 않아 0/1 실패다(도구 한계). 펌웨어 응답을 흉내 내면 35/35 확인됐다. 단 10.88초를 넘는 답은 펌웨어가 거부하고, 남은 530KB를 한 글자 명령으로 실행한다. 실측 최장 답은 10.4초로 한도에 바짝 붙어 있다.

### 문제
#### Critical
**C1. LLM 경로에서 마이크 소켓을 10~20초 읽지 않아 업링크가 끊긴다 — 그 사이 한 말은 사라지거나 늦게 처리된다**
- **위치:**
  - `voice_assistant.py:561-571` — `ask_async` → `spk.play("checking")` → `th.join(timeout=LLM_TIMEOUT_SEC+2)`
  - `:586` — `spk.send(…, expect=True)` → `_drain` 최대 15초
  - `:462` — 끊김 감지 후 `sleep(3)`
  - 펌웨어 `micUplinkTask` — `c.write != n` 이면 `c.stop()`
  - arduino-esp32 3.3.10 `NetworkClient::write` — select 1초 × 10회 뒤 부분 반환
- **무엇이 일어났나:** 질문 직후 데몬의 Recv-Q가 3.5초 만에 113,664~117,760B에서 멈췄다(파이 커널 실측, 약 3.6초 분량). 그 뒤 송신 쪽 write가 10.01초 막혀 끊겼다. LLM 경로(타임아웃 포함) 26회 중 24회 끊김, 2회는 6.4초·8.4초 막혔다가 회복했다(그만큼 소리 유실). 데몬은 답을 다 낸 뒤에야 EOF를 보고, 3초 쉰 다음 재연결하고 `spk.reset()` 한다.
- **재현:** `/tmp/claude-1000/r3/r3h.py s3_warm` 등. `events.log` 에 `mic_write_blocked {"sec": 10.01}` → `mic_uplink_drop_fw` 가 찍히고, `daemon.log` 에 `🔴 업링크 끊김 — 다시 붙는다` 가 찍힌다.
- **시연·운영자가 겪는 일:** 질문 약 3.6초 뒤부터 답 끝 +3초까지(약 13~20초) 귀가 먹는다. s3b에서는 앞 답(10.4초)이 끝난 직후 말한 「가디언 / 챔버 벤트 눌러도 돼?」가 통째로 사라졌다(들림 0).
- **확인 수준:**
  - 파이 쪽 수신창 포화: 재현(실측).
  - 업링크 끊김: 펌웨어·코어 소스대로 흉내 내 재현. 실물 확인은 ⏸.
  - 9/7 실HW 때는 A 갈래라 막히는 시간이 1~2초여서 드러나지 않았다.
- **고치는 방향:** 마이크 수신을 별도 스레드로 빼서 대기·재생 중에도 소켓을 계속 비운다. `del buf[:]` 대신 「대기 중 들어온 소리 버리기」를 실제로 수행한다. 펌웨어가 write 실패 때 끊지 말고 버리게 하는 것도 대안이다.

**C2. 콜드 모델은 데몬 요청으로는 영영 데워지지 않는다**
- **위치:** `voice_llm.py:65`(`urlopen` timeout = `config.LLM_TIMEOUT_SEC`) · `config.py:467`(15). 예열·`keep_alive` 없음.
- **무엇이 일어났나:**
  - s4에서 질문 3건 모두 15.02초 타임아웃이 났다. 셋째 질문은 첫 요청 약 75초 뒤였는데도 미적재였다.
  - 따로 확인: `curl -m 15` 로 끊은 뒤 5초 간격으로 85초까지 `/api/ps` 를 봤는데 계속 빈 목록이었다. 클라이언트가 끊으면 적재가 취소된다.
- **재현:** 모델이 내려간 상태에서 데몬을 띄우고 아무 질문이나 한다. 몇 번을 반복해도 같다.
- **시연·운영자가 겪는 일:** 파이2를 부팅한 직후나 5분 넘게 질문이 없어 모델이 내려간 뒤부터는, 질문마다 17.7초 기다렸다가 「답변할 수 없습니다」(공구 질문만 A 답)가 나온다. 사람이 따로 데우기 전까지 회복되지 않는다.
- **확인 수준:** 재현함.
- **고치는 방향:** 데몬 기동 때 긴 타임아웃(≥90초)으로 예열한다. 요청에 `keep_alive` 를 시연 시간 이상(또는 -1)으로 넣는다. 주기적으로 핑을 보낸다. 콜드를 감지하면 「준비 중」을 안내한다. 예열은 `num_ctx` 2048로 해야 재적재가 없다(2048로 예열했을 때 재적재 없음을 확인).

**C3. 설계 질문 2종에 LLM이 순서 위반 버튼을 안내한다**
- **위치:** `voice_card.py:119·132`(「지금 눌러야 할 버튼 B2」·「그 다음에 올 단계 … 버튼 B3」) · `verify_answer` `voice_card.py:172-190`(then↔now만 비교하고, 문장 속 버튼이 현재 버튼인지는 보지 않는다).
- **무엇이 일어났나:** 상태 = 2단계(B2).
  - 「펌프퍼지끝났어」 → 「…3단계 「전극 냉각」으로 진행하려면 버튼 B3를 누르시면 됩니다.」 3/3.
  - 「가디언 지금 다음 순서 뭐야?」 → 「…버튼 B3를 누르시면 됩니다.」 2/2.
  - 「전극 냉각 다 됐는지 확인해」 → 「…B3를 눌러 진행할 수 있습니다.」
  - 직접 호출 「지금 할 일을 순서대로 자세히」 → 「…이때는 버튼 B3를 누르시면 됩니다.」
  - 검산은 전부 「일치」였다.
  - GUI는 B2를 누르면 서브 작업을 돌리고, 그동안 `expected_step` 은 2에 머문다(`safety_console.py:1002-1060`). 그래서 이 상태에서 B3는 언제 눌러도 오답이다.
- **재현:** temperature 0이라 같은 카드·같은 질문이면 늘 같은 답이 나온다.
