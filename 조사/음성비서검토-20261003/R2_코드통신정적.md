## R2 음성비서 코드·통신 정적 검토 보고

### 요약
1. 업링크(8889)가 끊긴 줄도 모르고 멈춰 있는 상태(반열림)를 잡아내지 못한다. ESP32가 재부팅되거나 망이 바뀌면 음성비서가 아무 로그 없이 영구히 귀가 먹는다. 시연절차.md에 적힌 「3초마다 다시 붙는다」는 말이 이 경우에는 맞지 않는다.
2. 스피커 주소를 시작할 때 한 번만 정한다(마이크는 매번 다시 읽는다). LLM 답 합성음이 펌웨어 상한 240,000샘플(22.05 kHz에서 10.88초)을 넘으면 펌웨어가 본문을 읽지 않고 거절하고, 남은 PCM 바이트를 명령으로 해석한다. 둘 다 시연 중에 소리가 안 나거나 난장판이 되는 경로다.
3. 메인 루프는 LLM 대기·합성·재생 동안 마이크를 읽지 않는다. 대기가 약 13초를 넘으면 ESP32가 업링크를 스스로 끊는다(추론). `del buf[:]`는 커널 소켓에 쌓인 소리를 버리지 못하므로 G11 처방은 실제로 아무것도 하지 않는다.
4. 알려진 문제 ①~⑥은 모두 확인했다. ⑤는 원인을 더 좁혔다: 조각 크기보다 `_frame_rms`를 두 번 돌리는 것과 리스트를 ndarray로 바꾸는 비용이 크다. ndarray로 그대로 넘기면 6초 버퍼 1회가 17.0 ms에서 1.16 ms로 준다. ⑥은 「작업 시작 전」(notready)으로 판정이 끝났다.
5. `fake_glass`는 펌웨어 응답을 하나도 보내지 않는다. 오프라인 리허설과 selftest 모두 메인 루프(`run()`)를 전혀 시험하지 않는다.

### 문제

#### Critical

**C1. 업링크 반열림을 감지하지 못해 영구히 귀가 먹는다**
- **위치**: `Demo/voice_assistant.py:446-448`(`except socket.timeout: continue`), `:249`(`settimeout(5)`)
- **무엇이 틀렸나**: recv 5초 타임아웃을 횟수 제한 없이 삼킨다. 재접속은 EOF나 OSError가 올 때만 한다. 파이는 이 소켓에 아무것도 보내지 않고 keepalive도 꺼져 있어서, 상대가 사라져도 RST를 받을 계기가 없다.
- **시연에서 겪는 일**: ESP32가 재부팅되거나(배터리 전압 강하·전원 스위치) WiFi 재결합·주소 변경으로 lwIP 연결 상태를 잃으면 FIN/RST가 오지 않는다. 그 뒤로 영원히 timeout→continue만 반복한다. 호출어를 못 들으니 띠링도 없고, 그러니 스피커 채널도 다시 붙지 않는 교착이다. 로그에 「업링크 끊김」조차 찍히지 않아 시연절차.md:134의 대응표로도 진단할 수 없다. 운영자는 부팅 띠링은 듣는데 비서가 전혀 반응하지 않는 상태를 겪는다.
- **근거**: 펌웨어는 손님이 붙어 있는 동안 32 KB/s(1024 B 조각)를 쉬지 않고 보낸다(`glass_voice.ino:446-451`). 따라서 5초 동안 0바이트가 왔다면 링크가 죽었다는 확정 신호인데, 코드는 이를 버린다.
- **확인 수준**: 코드로 확인. 반열림은 TCP 표준 동작에 근거한 추론.
- **고치는 방향**: 연속 타임아웃 2회(10초)면 재접속한다. 또는 `SO_KEEPALIVE`에 `TCP_KEEPIDLE` 3·`INTVL` 1·`CNT` 3을 준다.

**C2. 스피커 주소가 시작할 때 고정된다**
- **위치**: `voice_assistant.py:264-273`(`Speaker.__init__`·`_ensure`가 `self.ip`), `:433`(`Speaker(ip)`)과 `:438`(마이크는 `get_ip=esp_ip`로 매번 다시 읽음)
- **무엇이 틀렸나**: 업링크 재접속 경로(`:463-465`)도 `spk.reset()`만 하고 주소는 옛 것 그대로다.
- **시연에서 겪는 일**: 통신경로 폴백(iptime→폰→파이AP)이나 DHCP 변경으로 주소가 바뀌고 `.camera_ip`를 갱신해도, 마이크만 새 주소로 붙는다. 띠링과 모든 답은 옛 주소로 나가 실패한다. 로그에만 남고 소리는 안 난다. 머리말(`:10-11`)과 `esp_ip` 독스트링(`:182-183`)이 약속한 「폴백을 따라간다」가 절반만 사실이다.
- **확인 수준**: 코드로 확인. 발동하려면 운행 중 주소 변경이 있어야 한다.
- **고치는 방향**: `Speaker`가 `ip_getter`를 받아 `_ensure` 때마다 다시 읽는다. 마이크가 실제로 붙은 주소를 공유한다.

**C3. 긴 LLM 답이 펌웨어 상한을 넘으면 명령 동기가 깨진다**
- **위치**: `glass_voice.ino:271-278`(`n > MAX_SAMPLE`이면 FAIL 후 **본문을 소비하지 않고** return), `:86`(`MAX_SAMPLE` 240,000), `Demo/voice_tts.py:49`(`frame()`에 길이·레이트 검사 없음), `voice_assistant.py:586-591`
- **무엇이 틀렸나**: 남은 PCM·체크섬·`P\n` 바이트가 `audioCmdTask`에서 한 글자씩 `handleCmd`로 해석된다. 하위 바이트 기준으로 대략 수천 번, `R`(녹음)·`r`(3초 녹음 후 재생, 삑 소리 포함)·`p`/`P`(재생)·`D`(최대 480 KB 덤프)·`1`~`5`(음량)·`B`(띠링)가 실행된다.
- **시연에서 겪는 일**: 파이 쪽은 `[FAIL]`을 보고 `_drain`을 끝내고 대체 답을 내지 않는다. 결과적으로 답은 침묵이고, 글라스에서는 엉뚱한 삑·녹음·재생이 난다. 다음 `_drain`은 쓰레기 명령에서 나온 `[재생 완료]`를 자기 확인으로 잘못 읽을 수 있다.
- **근거(실측)**:
  - 기존 wav에서 잰 TTS 속도는 평균 6.0음절/초다. 상한은 약 65음절, 대략 89자에 해당한다.
  - 그럴듯한 두 문장 답을 실제로 합성해 쟀다: 「현재 2단계 펌프/퍼지 단계이며 … 필요한 공구는 렌치입니다.」(75자) 9.17초로 여유 1.72초, EMO 안내(61자) 7.15초, 결과 안내(65자) 8.34초.
  - `LLM_NUM_PREDICT` 80토큰이면 이 상한을 넘는 답도 나올 수 있다.
  - 같은 동기 깨짐은 W 본문 도중 8초 정체(`:291-296`)에서도 난다.
- **확인 수준**: 펌웨어 경로는 코드로 확인. 상한 초과 빈도는 추론이다(여유가 작다는 것은 실측).
- **고치는 방향**: 파이에서 보내기 전에 n ≤ 240,000이고 레이트가 8,000~24,000인지 검사하고, 넘으면 두 문장까지 자르거나 A 갈래로 대체한다. 펌웨어는 W 거절 시 n×2+6바이트를 버리거나 손님을 끊는다.

#### Important

**I1. 메인 루프가 막히면 업링크가 끊기고, G11 처방은 효과가 없다**
- **위치**: `voice_assistant.py:561-571`·`:578-597`(join·합성·재생 확인 대기가 모두 메인 스레드), `:571` `del buf[:]`, 펌웨어 `:448-451`, arduino-esp32 3.3.10 `NetworkClient.cpp:386-447`
- **무엇이 틀렸나**:
  - (a) 대기 중에는 recv를 하지 않으니 `buf`는 자라지 않는다. 쌓이는 곳은 커널 수신 큐다. 따라서 `del buf[:]`는 「5~7초 동안 쌓인 소리」를 버리지 못한다. 주석 `:568-570`이 동작과 다르다.
  - (b) 파이 수신 큐는 약 3초 분량이면 창이 0이 된다. 루프백에서 쟀을 때 98,304 B = 3.07초였다(`tcp_rmem` 131072). 그 뒤 펌웨어 `c.write`가 진척 없이 1초짜리 select를 10번 기다리다 짧게 반환하고, 펌웨어가 `c.stop()`으로 업링크를 끊는다.
- **경로별로 마이크를 읽지 못하는 시간**:

| 경로 | 마이크 못 읽는 시간 | 업링크 끊김(문턱 약 13초) |
|---|---|---|
| notready | 약 2.5초 | 아니오 |
| LLM 예열됨 | STT 0.2 + LLM 5~7 + 합성 0.4~1 + 재생 5~9초 ≈ 11~17초 | 긴 답이면 끊김 |
| LLM 콜드·타임아웃 | join 17 + 대체 재생 약 2초 | 반드시 끊김 |

- **시연에서 겪는 일**:
  - 끊기고 나면 커널에 남은 소리(대기 앞 3초 — 「확인해 보겠습니다」 반향 포함)를 처리한 뒤 EOF → 3초 sleep → 재접속한다. 이 3초 남짓 동안 호출어를 놓친다.
  - 재접속 시 `spk.reset()`이 명령 채널도 버린다. 그래서 `:434-436` 주석이 기록한 「연결 설정과 겹친 첫 띠링이 안 들림」 조건이 매번 다시 생긴다.
  - 대기 앞 3초 안에 다시 「가디언」을 말하면, 답이 끝난 직후 재호출된다. G11이 재발하는 것이다.
- **확인 수준**: 추론(코드 + 로컬 계측). 실HW 확인 필요.
- **고치는 방향**: 마이크 수신을 별도 스레드로 빼서 늘 읽고, 대기 끝에 타임스탬프 기준으로 버린다. 최소한 대기 직후 non-blocking으로 소켓을 비우고, 재접속 직후에는 `spk.send(b"")`로 미리 붙인다.

**I7. 보안**
- **Ollama**: 파이2가 `0.0.0.0`에 인증 없이 열려 있다. 같은 망의 누구든 다음을 할 수 있다.
  - `/api/generate` 독점 → 우리 호출 타임아웃 → 대체 문장
  - `/api/delete`로 `gemma4:e2b-it-qat` 삭제 → LLM 영구 실패(다시 받으려면 인터넷 필요)
  - 큰 모델 `/api/pull`·적재 → 메모리 축출·디스크 고갈 → 콜드 적재 반복
  - 버전에 따라 과거 CVE(경로 탐색 등) 노출 — 버전은 확인 못 함
  - 폰 핫스팟이나 학교 WiFi면 범위가 그만큼 넓다.
- **ESP32 8890**: 무인증이고 「새 손님으로 갈아타기」(`glass_voice.ino:405-414`) 규칙이 있다. 누구나 붙어서 작업자 귀에 임의 음성을 재생하거나 음량을 바꿀 수 있다. `R 10`→`D`로 마이크 녹음을 덤프할 수 있다(삑 소리가 나 은밀하지는 않다). 파이와 서로 끊어내는 핑퐁도 생긴다.
- **ESP32 8889**: 손님 1명 규칙이다. 파이가 빠진 사이(I1에 따라 긴 답마다 생길 수 있음) backlog에서 기다리던 다른 손님이 먼저 accept되어 마이크를 **소리 없이** 도청할 수 있다. 그동안 파이 연결은 backlog에 머물러 C1과 같은 귀먹음이 된다.
